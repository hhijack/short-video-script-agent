# 05-retrospective.md — 最难问题、学习收获、下一步

## 最难的问题：让「动态决策」真实发生而不是看起来发生

**问题**：项目要求明确「仅有固定条件分支、自动重试、预设决策日志不算完成 ReAct」。第一版 Mock 模型按「稿次」维护内部状态（gen=1/2），结果在 case1 首稿检查失败后，状态机把「刚检查完的稿」误判成「下一稿」，直接走了「压缩稿仍不通过 → 无法满足」的终止分支，把本该成功的用例跑成了失败。

**定位与修复**：把 trace 全量打印后逐步对照，发现是「当前稿」的推导时机错了——决策时用的稿次应该是「刚被检查的那一稿」，而不是「下一次要交的稿」。重构为完全无状态：所有判断（当前是首稿还是压缩稿、重试了几次、读了哪些素材）都从观察历史推导，与真实模型「只看上下文」的工作方式一致。修完顺带消灭了另一类隐患：状态不会再在多次 decide 之间悄悄漂移。

**收获**：ReAct 循环里「模型无状态、状态在历史里」不只是架构洁癖——它让「下一步由观察决定」变成结构性保证，而不是靠程序员在分支里记得维护状态。

## 真实模型实测带来的两个意外（2026-10-30 批次 1，doubao-seed-2.1-lite）

1. **模型不天然遵守产品约束**：case2（缺目标时长）首跑时真实模型自行假定 50.3 秒把任务做完了——它没坏，只是「缺关键信息必须先问」是产品规则而非模型本能。把约束写进 system prompt 后重跑即正确请求补充。教训：**每条产品约束都要么做成工具/检查项，要么显式写进模型指令，然后必须用用例验证**，不能假设「聪明的模型自然会这么做」。
2. **工具失败时的降级比预期聪明**：case4 里估算工具持续失败，模型没有像 Mock 策略那样重试后放弃，而是按「工具文档里公开的计算口径」自行估算，再借 check_rules 交叉验证（批次 1 中 R6 还真拦下了它一处语速违规）。这提示验收点设计要考虑「模型绕过故障工具」的路径：自估有风险（总时长无第二来源），但也确实是可用的降级策略——两版行为我们都如实保留并对照（examples/ vs examples_real/ 的 case4）。
3. **（批次 2 补充）模型的输出结构也要审计**：对抗性审查发现首跑的 output 里 risks 是整句字符串、status 是口语表述——决策对了，交付字段却没按协议来。修复是确定性结构规整 + 修复留痕（trace `output_normalization`），「模型说什么」和「系统收什么」必须是两道工序。

## 其他值得记录的判断

1. **估算与检查共用一个口径**：时长估算（4 字/秒）和规则检查 R6（语速上限 5 字/秒）如果各写各的，会出现「估算工具说合格、检查工具说不合格」的自相矛盾。工具族内部口径一致比单个工具聪明更重要。
2. **故障注入做在包装层**：不改任何工具实现就能复现「工具失败」，且对真实模型路径同样生效——测试基建与业务代码分离。
3. **Mock 也要按观察路由**：最初想用「预生成的动作列表」当 Mock，很快意识到它对故障注入和检索差异毫无反应，等于伪造动态决策；改成策略函数后，case1/3/4/5 四条路径自然分叉。

## 学习收获

- 把一条审核规则（事实可追溯）做成确定性检查项（R3 正则 + 原文比对），比「提醒模型不要编造」可靠得多——LLM 的诚实度不该是系统唯一的防线。
- trace 的设计直接决定可审核性：args 回显 + 完整观察 + 一句话决策依据，让「素材 ID、分镜时长和检查结果逐一对应」成为打开文件就能核对的事。
- 先写用例的数值目标（38→28）再倒推文案字数，比先写文案再凑数字高效。

## 下一步（按优先级）

1. **多模型对照**：真实模型路径已用 doubao-seed-2.1-lite 跑通（examples_real/），下一步换 2-3 个 OpenAI 兼容模型复测同一组用例，观察 case2/case4 这类约束与降级行为的模型间差异；
2. **R3 升级**：中文数字归一化 + 轻量语义匹配（如产品功能短语向量比对），降低绕过面；
3. **检索增强**：同义词扩展、按场景打分（开场/卖点/CTA 各自适配的素材类型）；
4. **交互闭环**：case2/case3 的「请求补充」目前以 questions 返回即结束，可做成多轮会话，用户补充后从断点继续。
